1. Project Overview
StopCheck is a SaaS platform that enables gravel cycling event organizers to automatically verify that all registered riders performed a complete 3-second stop at every marked stop sign on the course. The platform ingests rider GPS and wheel speed sensor data via Strava, Garmin Connect, or Wahoo API connections — or direct FIT file upload — and produces authoritative per-rider and per-event compliance reports that serve as the evidentiary basis for disqualification decisions.
1.1 Problem Statement
Gravel cycling events frequently route riders through public roads with legally required stop signs. Compliance is currently unenforceable at scale — race officials cannot be stationed at every intersection. This creates safety risks and fairness issues when competitive riders roll through stop signs to gain time advantages. No existing platform solves this problem automatically.
1.2 Core Value Proposition
Zero behavior change for riders who already upload to Strava, Garmin Connect, or Wahoo
Zero manual work for organizers after initial event setup
Defensible, sensor-based evidence for every compliance decision
Accessible to all event sizes — from 20-rider local races to 4,000-rider national events
1.3 Design Principles
Every product and engineering decision must be evaluated against these principles in order of priority:
Friction-free for riders — the ideal rider experience requires zero extra steps beyond what they already do
Friction-free for organizers — setup should take under 10 minutes per event
Defensible outputs — every compliance result must trace to raw sensor data
Graceful degradation — always offer a fallback path; never hard-block a user
Platform-agnostic — support all major head unit ecosystems equally
2. User Roles & Journeys
2.1 Race Organizer Journey
Registers on StopCheck platform (free account)
Creates a new event: name, date, location, distance category
Uploads course file (GPX or FIT) — platform accepts both formats
Platform auto-detects stop sign locations along the course corridor using OpenStreetMap Overpass API
Organizer reviews stop sign pins on interactive map, adjusts if needed (drag, add, remove)
Sets compliance rule: minimum stop duration (default 3 seconds), geofence radius (default 20 meters)
Platform generates personalized route email template with embedded OAuth connect buttons
Organizer copies template into their existing email tool (Mailchimp, Gmail, etc.) and sends to registered riders
Platform sends automated reminders to riders who have not connected 3 days and 1 day before event
After event: dashboard auto-populates as riders upload their activities
Organizer reviews violations, confirms disqualifications via two-step workflow
Exports PDF compliance report for official records
2.2 Rider Journey
Receives pre-event route email from organizer
Downloads course GPX or FIT file as normal
Clicks one Connect button (Strava, Garmin, or Wahoo) in the same email
Completes standard OAuth authorization popup — takes under 30 seconds
Rides the event using their existing head unit with wheel speed sensor
Uploads activity to their chosen platform as normal
Receives automated compliance report email within 1 hour of upload
Views personal stop-by-stop breakdown at their unique results URL
CRITICAL UX REQUIREMENT: The rider must never be required to visit the StopCheck website directly, create an account, or download an app. All interaction happens via email links and the standard OAuth popup they already recognize.

3.2 Data Flow Architecture
ORGANIZER SETUP FLOW
  1. Organizer uploads GPX/FIT course file → stored in S3
  2. Backend parses course coordinates → calls OSM Overpass API
     GET https://overpass-api.de/api/interpreter
     Query: node[highway=stop] within 30m of course corridor
  3. Stop sign nodes returned → stored as (lat, lon, sequence_number)
  4. Organizer edits on map → final stop signs saved to DB
  5. Platform generates unique rider tokens → embedded in email template
RIDER AUTHORIZATION FLOW
  1. Rider clicks Connect button in email
     URL: app.stopcheck.io/auth?event=XYZ&rider=ABC&platform=strava
  2. Redirect to platform OAuth endpoint
  3. Rider authorizes → platform returns OAuth code
  4. Backend exchanges code for access_token + refresh_token
  5. Tokens stored encrypted in DB, linked to rider+event record
POST-EVENT DATA INGESTION FLOW
  Option A — Webhook (Strava, Wahoo): platform pushes activity notification
  Option B — Polling (Garmin): backend polls /activities every 15 min post-event
  Option C — Manual upload: rider drops FIT file at their unique URL
  → All paths produce a FIT file stored in S3
  → Job queued: process_fit(rider_id, event_id, fit_file_path)
3.3 FIT File Processing Engine
This is the core analysis component. It must be implemented as a standalone, testable module with no UI dependencies.
3.3.1 FIT Parsing
Use the official Garmin FIT SDK (fitparse Python library or @garmin/fitsdk JS)
Extract record messages: timestamp, position_lat, position_long, speed, enhanced_speed
Speed field priority: use enhanced_speed if present, fall back to speed field, then GPS-derived speed as last resort
Flag any file that uses GPS-derived speed only — include warning in compliance output
Validate 1-second recording rate — if average gap between records exceeds 2 seconds, flag as insufficient resolution
3.3.2 Geofence Matching
For each stop_sign S in event.stop_signs:
  entry_records = []
  For each record R in rider.fit_records:
    distance = haversine(R.lat, R.lon, S.lat, S.lon)  # meters
    if distance <= geofence_radius (default 20m):
      entry_records.append(R)
  if len(entry_records) == 0:
    result = MISSED  # rider GPS never entered geofence
    # Note: check if course deviation explains this
  else:
    analyze_stop(entry_records, S)
3.3.3 Stop Detection Algorithm
def analyze_stop(records, stop_sign):
  min_speed = min(r.speed for r in records)  # mph or m/s
  zero_speed_records = [r for r in records if r.speed <= SPEED_THRESHOLD]
  # SPEED_THRESHOLD = 0.5 mph (accounts for sensor noise near zero)
  if len(zero_speed_records) == 0:
    return StopResult(status=FAIL, min_speed=min_speed, duration=0)
  # Find longest consecutive zero-speed window
  max_duration = longest_consecutive_window(zero_speed_records)
  # Uses timestamps: duration = last_record.timestamp - first_record.timestamp
  if max_duration >= STOP_DURATION_THRESHOLD (default 3.0 seconds):
    return StopResult(status=PASS, min_speed=min_speed, duration=max_duration)
  else:
    return StopResult(status=FAIL, min_speed=min_speed, duration=max_duration)

10. Crossing Guard Waiver System
Some stop signs on a course may have a crossing guard or race marshal posted on event day to manage traffic flow. Riders directed through by a crossing guard are not required to perform a full 3-second stop at that location. However, this waiver applies ONLY during official event hours on race day. It does not apply to pre-riding, course reconnaissance, or any activity recorded outside the official event window.
10.1 Organizer Setup — Marking Guarded Stops
During event setup in the stop sign map editor, organizers can mark any stop sign as 'crossing guard posted' for event day. This is a per-stop, per-event setting — not a global toggle.
In the map editor, organizer clicks any stop sign marker
Edit popover shows a toggle: 'Crossing guard posted on event day'
When enabled, the marker changes to a distinct visual (orange instead of red) to clearly differentiate it on the organizer's map
Organizer sets the official event window: start datetime and end datetime (e.g., 7:00 AM – 4:00 PM race day)
The event window applies globally to the event — it is not configurable per stop sign
Organizer must confirm: 'I confirm a certified crossing guard or race marshal will be posted at this location during the entire event window'
WARNING TO CODING AGENTS: The crossing guard waiver is time-gated. The compliance engine must check the rider's activity timestamp against the event window before applying the waiver. A rider who pre-rides the course two days before the event and rolls through a guarded stop is NOT exempt. This is a hard requirement — never skip the timestamp check.

10.3 Compliance Engine Logic — Crossing Guard Check
def evaluate_stop(rider, stop_sign, entry_records, event):
  # Step 1: Check if this stop has a crossing guard posted
  if stop_sign.crossing_guard:
    # Step 2: MANDATORY — check if activity is within the official event window
    activity_start = rider.activity_start_timestamp
    activity_end   = rider.activity_end_timestamp
    within_event_window = (
      activity_start >= event.event_window_start AND
      activity_end   <= event.event_window_end
    )
    if within_event_window:
      # Waiver applies — rider does not need to stop here
      return StopResult(
        status          = 'guard_waived',
        min_speed_mph   = min(r.speed for r in entry_records),
        stop_duration_s = None,
        note            = 'Crossing guard posted — stop not required during event'
      )
    else:
      # Pre-ride or post-event activity — normal compliance rules apply
      # Fall through to standard stop detection below
      pass  # DO NOT return here — continue to standard check
  # Standard stop detection (applies when no guard, or outside event window)
  return standard_stop_detection(entry_records, event)

The organizer dashboard and rider detail view must clearly distinguish crossing guard waivers from genuine compliance:
Stop sign dots in the rider table: green = pass, red = fail, orange = guard waiver, gray = pending
Guard-waived stops display as 'Guard waiver — event day' in the rider detail stop card

10.5 Pre-Ride Compliance Reports
Riders frequently pre-ride event courses in the days before an event. StopCheck will process any activity on the course route that uses the rider's connected platform account — not just the race day activity. Pre-ride compliance reports are informational only and cannot result in disqualification. However, they must accurately reflect the crossing guard rule:
Pre-ride activities are labeled 'Pre-ride' in the rider's results history
Pre-ride reports show full stop compliance — crossing guard waivers do NOT apply
Organizers can see pre-ride activities in the rider detail view — useful for identifying riders who habitually roll stops
Pre-ride results are never included in the official event compliance determination
This feature provides real safety value: riders who see their own pre-ride compliance report showing multiple failures are far more likely to stop correctly on race day. Consider making pre-ride reports a prominent feature in rider-facing marketing.

11.2 FIT File Processing — Data Stripping Pipeline
def process_fit_file(fit_file_path, event_stop_signs):
  # Step 1: Parse entire FIT file into memory only — never write to DB yet
  all_records = parse_fit(fit_file_path)
  # Step 2: Extract ONLY records within geofence windows
  # Discard everything else immediately — do not log, cache, or store
  geofence_records = {}
  for stop in event_stop_signs:
    window = [r for r in all_records
              if haversine(r.lat, r.lon, stop.lat, stop.lon) <= 50]  # 50m buffer
    geofence_records[stop.id] = window
  # Step 3: Strip sensitive fields from even the geofence records
  # Keep ONLY: timestamp, speed, distance_from_stop
  # Discard: precise lat/lon within stop zone, heart_rate, power, cadence
  for stop_id, records in geofence_records.items():
    geofence_records[stop_id] = [
      { 'timestamp': r.timestamp,
        'speed': r.speed,
        'dist_from_stop': haversine(r.lat, r.lon, stop.lat, stop.lon) }
      for r in records
    ]
  # Step 4: Run compliance analysis on stripped records
  results = analyze_compliance(geofence_records, event_stop_signs)
  # Step 5: Delete the original FIT file from storage
  delete_file(fit_file_path)  # S3 delete — immediate, not soft-delete
  # Step 6: Store only the compliance results and the minimal record windows
  store_results(results)  # compliance_results table only
  return results
  # What is NEVER stored: full GPS track, home location, heart rate,
  # power, cadence, precise lat/lon within stop zones, full ride duration
11.3 OAuth Token Security
All OAuth tokens encrypted at rest using AES-256-GCM before writing to database
Encryption key stored in environment variable only — never in code, never in DB
Access tokens deleted from database immediately after the FIT file has been successfully retrieved and queued for processing
Refresh tokens deleted after event_window_end + 48 hours — after this point, re-authorization would be required for any future event
Token table has a scheduled cleanup job running every 6 hours to purge expired tokens
If a rider disconnects their account, all tokens for that rider are deleted synchronously — not batched
11.4 Infrastructure Security
FIT files stored in private S3/R2 bucket — no public access under any circumstances
All file access via signed URLs with 15-minute expiry maximum — never 1 hour
S3 bucket versioning disabled — deleted files are gone immediately, not recoverable
All API endpoints validate JWT on every request; no unauthenticated endpoints except OAuth callbacks and rider hub pages (which are token-authenticated via URL)
Webhook endpoints verify platform-specific signatures before processing: Strava uses SHA-256 HMAC, Garmin uses OAuth signature, Wahoo uses bearer token verification
Rate limiting on all endpoints: 20 requests/minute per IP on OAuth callbacks, 100/minute on general API
All inter-service communication over HTTPS/TLS 1.3 only — reject HTTP and TLS < 1.2
Database: parameterized queries only — zero string concatenation in SQL throughout entire codebase
No third-party analytics SDKs on rider-facing pages — no Google Analytics, no Meta Pixel, no tracking of any kind
Dependency audit: run npm audit / pip audit in CI on every deploy; block deploys with critical vulnerabilities
11.5 Application Logging Rules
Never log OAuth tokens, refresh tokens, or encryption keys — add log sanitization middleware that redacts these patterns
Never log full FIT file contents or GPS coordinates
Never log rider email addresses in application logs — use rider_id (UUID) only
Log retention: application logs auto-deleted after 30 days
Error tracking (Sentry): configure data scrubbing to strip PII from error reports before transmission

14. Glossary
Term
Definition
FIT file
Flexible and Interoperable Data Transfer — binary file format produced by Garmin, Wahoo, and other GPS devices containing timestamped activity data
Geofence
A virtual geographic boundary defined by a center point and radius; riders enter the geofence when their GPS coordinates are within the specified radius of a stop sign
OAuth2
Industry-standard authorization protocol allowing users to grant third-party applications access to their data without sharing passwords
Wheel speed sensor
A physical sensor attached to the bicycle wheel that measures rotation; produces more accurate low-speed data than GPS-derived speed
Stop compliance
A rider is considered compliant at a stop sign if their wheel speed sensor recorded <= 0.5 mph for a continuous 3-second window while inside the stop sign geofence
DQ / Disqualification
Removal of a rider from official results due to stop sign non-compliance; must be confirmed by an organizer before taking effect
Haversine formula
Mathematical formula for calculating the great-circle distance between two points on a sphere given their latitude and longitude
1-second recording
GPS head unit setting that records a data point every second; required for accurate stop detection; contrast with 'smart recording' which may skip seconds
GPX
GPS Exchange Format — XML-based file format for GPS tracks and waypoints; commonly used for course distribution
OSM / OpenStreetMap
Open-source global map database; used to auto-detect stop sign locations along event courses
Crossing guard waiver
An exemption applied to a specific stop sign when a certified crossing guard or race marshal is posted there during the official event window. The waiver applies only to activities recorded during the event window — pre-ride activities are subject to full stop compliance regardless.
Event window
The official start and end datetime of the race event, set by the organizer. Used to gate crossing guard waivers — only activities within this window receive the exemption.
Data minimization
The practice of collecting only the data strictly necessary for compliance analysis and deleting it as soon as it is no longer needed. StopCheck stores only speed records within stop sign geofence zones — never full GPS tracks.
